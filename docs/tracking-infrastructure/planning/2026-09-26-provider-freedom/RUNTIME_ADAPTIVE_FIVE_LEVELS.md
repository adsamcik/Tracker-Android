## 1. New requirement and recommendation

Latest user text supplied by the coordinator:

> The adaptive system should be able to leverage hints from multiple sources that tell it whether the user is moving, stationary, what is the settings what balance between quality and power it should use. This includes whether session is active and more, fill in all the types. The system should then based on this adapt the tracking and setups so that its working reliably and trustworthy, especially trying to balance the value. The goal is that everything should work through a central systém and it should adapt to balance what the user wants if they start a session they want to prefer quality over power otherwise based on settings other preferences may be there. Use a 5 step configuration for balance of power and performance and figure out the best system that can support it.

Settled: one independent adaptive collection system; exactly five selectable balance levels; multi-source hints; live sessions prefer quality and organize data; retrospective sessions organize existing facts without acquiring data. Source choice, separate purpose consent, immutable acquisition authority, local-only storage and the phase boundary remain. The earlier ambient-only → outside-sessions-only mapping is withdrawn: baseline eligibility can continue during live sessions, including sources not participating in session capture.

**Recommendation:** extend `CollectionMotionController` into the bounded hint/fusion part of one revisioned decision path, use `SemanticAcquisitionPlanFactory` for profile construction, and retain `SourcePlanResolver` as the sole final per-source constraint resolver. Existing broker/controllers apply the result. Fold legacy policy outputs into this path or derive compatibility output from its result; do not add a third independent policy engine, plugin graph, learning system or optimization service.

Five **preferences** are distinct from motion **states**, provider **mechanisms**, source **enablement**, and actual **achieved quality**. Off is not one of the five levels. A level never grants permission, enrolls a source or guarantees a sampling rate. No generic percentage-per-hour battery estimate is justified.

“Source off” controls Tracker's independent acquisition demand and stored product for that source. An Android fused Location provider may internally use radios or other sensors; the app must not promise physical chip inactivity from its own Wi-Fi/Cell switch. Optional enrichment still creates no independent app acquisition demand.

## 3. Central decision path and precedence

Use one serialized reconciliation path in the existing coordinator/application-scope machinery. A small immutable input snapshot and pure decision function are enough; no new generalized event bus. Existing source-local owners retain their locks and Android calls.

1. **Load one consistent intent/authority snapshot:** source baseline and focus eligibility, purpose consent, selected overall/source balance, explicit hard limits, live demand leases, collected-data/deletion/retention and rollout authority. Missing/invalid authority fails closed for that scope.
2. **Qualify bounded hints:** admit only allowed current-boot/source-authority observations or authenticated control evidence; derive transient facts with age, interval, uncertainty, confidence class and independent origin. Discard expired/replayed/wrong-generation/deleted-authority hints; imported history and retrospective grouping cannot steer current collection.
3. **Determine intent separately from motion:** baseline preference, live quality target and explicit temporary feature demands are requirements, not confidence votes. Determine UNKNOWN/STATIONARY/PEDESTRIAN/VEHICLE/MOVING from qualified evidence; conflict remains explicit.
4. **Construct source-specific desired profiles:** choose useful mechanism/cadence/batch targets within the authorized adaptive envelope. Apply a live-session quality preference only to participating sources; baseline-only sources remain eligible and independent.
5. **Resolve limits and achievable obligations:** privacy/Off/pause → platform/legal/hardware constraints → safety/resource feasibility → explicit user hard limits and source contract floors → live quality target → baseline preference/cost savings. Soft target failure is reported, not elevated into permission or a false hard minimum. Hard consumer constraints remain strict.
6. **Persist and apply through existing plan/broker:** store immutable desired revision and exact contracts before registering/reconfiguring; keep source-local APPLIED/DEGRADED/BLOCKED/FAILED results separate. Only changed physical fingerprints cause hardware work; reason-only/organization changes do not restart providers.
7. **Observe actual outcomes:** delivery freshness, qualified accepted observations, coverage/gaps, retirements, failures/backoff and bounded writer pressure update the next decision. Applied plan is not proof of data. Expose a concise cause such as “Session detail requested; Location limited by permission.”

**Important floor correction:** the proposed live target `max(baseline,4)` is a preference. It must not be translated into an impossible hard direct floor that causes resolver `:92` to disable a valid baseline. Resolve each demand's achievable contract before combination; retain independently authorized useful baseline, mark focus target unsatisfied, and refuse to claim focus quality. A real incompatible hard demand is rejected/degraded for its consumer rather than silently relaxing its semantics or discarding unrelated consumers. Exact broker status/contract representation is a pre-edit design seam.

Hard constraints may make a promised floor impossible. Then mark the affected requirement unsatisfied and stop/limit that source as required; do not pretend both safety and fidelity were met. Available siblings continue unless a shared durable storage/authority failure genuinely prevents trustworthy admission. Correct the current service-wide internal-failure path only for typed source-local failures; do not conceal global corruption or deletion barriers.

## 5. Five balance levels

Proposed labels agreed with Product and coordinator: **1 Power first · 2 Favor power · 3 Balanced · 4 Favor detail · 5 Detail first**. Default for a newly chosen adaptive profile:3. They describe preference and target response, not percentages, physical accuracy or five different mechanisms for every source.

| Level | Baseline intent within consent/capability | Cost/value behavior |
| --- | --- | --- |
| 1 Power first | Preserve the cheapest useful supported evidence; accept delayed/sparse delivery explicitly. | Prefer batching/opportunistic work, no optional active radio attempts. Never change requested sources to Off or label gaps complete. |
| 2 Favor power | Improve useful change detection over1 without broad high-rate collection. | Moderate batches and conservative confirmation/recovery; same physical radio mechanism may be appropriate as1. |
| 3 Balanced | Default useful history and response without sustained maximum acquisition. | Shorter batches while moving or quality is at risk; reduce only with evidence and preserved floors. |
| 4 Favor detail | Prioritize continuity/freshness and useful detail; proposed minimum desired preference during a live session. | Faster wake/recovery and lower latency on participating sources; still avoid futile probes, duplicates and unnecessary stable-state writes. |
| 5 Detail first | Strongest supported selected-source targets within explicit caps. | Least batching/most responsive useful profile where supported; still adaptive under stationary evidence and hard limits. Never “all sensors always on.” |

**Live versus baseline:** proposed `focusPreference = max(sourceBaselinePreference, 4)` for participating sources, bounded by explicit user ceilings and legal/safety feasibility. Source baseline defaults to the overall level; an optional override in existing source Details uses the same five choices. No second always-visible slider. End focus restores the configured baseline, not a hardcoded lowest tier. Retrospective creation/editing has no effect. Automatic *live* sessions receive the same preference once legally admitted; trigger evidence and consent remain separate.

Existing custom limits are hard constraints, not reinterpreted as soft baseline values. A user who previously constrained Location must not silently get a faster profile merely because focus now prefers4. If the new adaptive envelope would exceed their old explicit contract, preserve old behavior and require explicit adoption/change. UI reports the cap instead of silently granting the focus target.

## 7. Balancing information value and cost without another optimizer

Use a fixed decision order, not a learned utility score:

1. Satisfy durable safety/consent and the useful source product's true minimum.
2. Prefer preventing an unrecoverable gap or meeting an active user's detail request over a redundant update.
3. Prefer already available shared observations and batching over a new physical request when they satisfy the same requirement.
4. Consider a permitted stronger request only when current qualified quality/freshness is insufficient and the source can plausibly improve it.
5. Stop optional attempts after their finite existing budget/cooldown; no response, throttling or unchanged cache does not justify a retry loop. Resume on the correct platform signal or an authorized retry deadline.

Battery percent/saver are soft cost pressure unless an explicit approved safety policy says otherwise; thermal/legal inability and critical storage/admission failure are hard constraints. Recommend retaining source minimums rather than blanket GPS-off at20%. The following concrete response table is part of the same proposed envelope:

| Condition | Baseline response | Live focus response |
| --- | --- | --- |
| Battery at or below20%, not charging | Reduce the configured source preference by one level, minimum1; clear this reduction after reaching25%. | Preserve desired `max(configured preference,4)`; disclose a real quality limitation, not an automatic no-GPS downgrade. |
| Battery at or below10%, not charging | Prefer level1; release critical cap after15%, then apply any remaining low-battery rule. | Preserve the quality target subject to hard constraints; one quiet relevant critical-battery notice per crossing, not repeated nags. User pause/limits always remain available. |
| Android Battery Saver | Same one-level baseline pressure; do not stack it with the20% reduction into a two-level penalty. Any actual OS restriction is a separate hard limit. | Keep focus target; comply with actual OS restrictions and explain unmet quality. |
| Charging | Remove only battery-percentage reduction; recompute from the saved preference, never escalate above it merely because power is connected. Saver/thermal/legal restrictions remain independent. | Same target as before; no additional source or detail enrollment. |
| Battery reading unknown | No invented100% reading or inferred critical state; keep the configured preference and known OS constraints. | Same; status may say battery state unavailable only where relevant. |
| Severe thermal/resource inability | Drop optional probes and choose the minimum useful supported safe profile; if no safe plan can meet a hard requirement, suspend the affected source/requirement and report that reason. | Target remains requested but may be unmet; hard safety/legal constraints win. Never claim achieved fidelity while violating either safety or source contract. |

Recompute from saved preferences on every consistent snapshot; reductions must not repeatedly ratchet an already reduced level. Percent hysteresis applies only to valid readings, and higher-priority hard limits need immediate handling. This is a proposed policy choice—not measured optimality—and the low-battery live-session tradeoff should be visible in the single approval packet.

At severe limits, report requested versus achieved quality and gaps; level5 or a live session does not override safety. No independent legacy global tier cap remains downstream of this arbiter.

One central desired plan does not require one all-or-nothing apply transaction across hardware. Each owner returns its exact outcome; successful siblings remain. Constrain callback/WAL memory, IO/retry concurrency and materialization backlog through existing queues and injected dispatchers. A full queue/storage failure must produce a bounded retry or explicit lost coverage, never “recording complete.” Do not repeatedly collect expensive data the current pipeline cannot durably accept.

Run decisions on meaningful input changes: intent/consent, live lease, new qualified hint, hint/dwell expiry, legal/availability change, applied failure/backoff completion, or resource state. Use existing coalesced wake/tick mechanisms and lifecycle subscriptions. No permanent sensor polling or exact-alarm service is introduced. Stop observing/acquiring when no authorized scope needs it; a sessionless host still needs its separately reviewed legal platform implementation.
