## 2. Location: selected host, provider and handoff design

### 2.1 Passive baseline is a complete product, not an active session

**Recommendation:** add `LocationAmbientPurposeOwner` beside existing purpose owners, and a shared Location controller in the registry. Its baseline demand resolves to a **system-rearmable passive PendingIntent** when no stronger lawful Location demand exists. Use FLP `PRIORITY_PASSIVE` when GMS is actually available; otherwise framework `LocationManager.PASSIVE_PROVIDER` with its PendingIntent overload. Both are existing platform/dependency options. Preserve the current backend selection intent; a runtime GMS failure does not silently start framework GPS before exact cleanup.

Register one explicit non-exported receiver, e.g. `PassiveLocationReceiver`, in the engine manifest. Use a generation-specific explicit Intent identity containing an opaque registration token in the data URI, never coordinates, consent grants or session IDs. Provider fill-in delivery needs a mutable PendingIntent on API31+; keep the component explicit and allow no mutable routing fields. Reconstruct and remove the exact PendingIntent from its durable generation identity. Use the framework provider-specific API on API26–30 and the LocationRequest overload where supported; do not assume batching or flush on the existing framework backend.

Initial passive request target: FLP passive priority, explicit minimum update interval30s, minimum displacement0m, no promised cadence; framework passive minimum30s/0m. This is an approved-envelope proposal, not an Android delivery guarantee. The passive path must not request an active fix to fill a gap. Preserve all qualified delivered observations; the admission age is the baseline's explicit contract, not receipt time invented as observation time. For this initial passive contract propose maximum item age120s, matching existing low-power Location age; older batches remain rejected/partial rather than relabelled fresh. A future historical batch product would be a distinct deliberate contract change.

Android documents PendingIntent FLP delivery for background use and process recreation; registrations can be removed by app reset/update/force-stop/cancellation. It also documents cached first deliveries. This supports the carrier choice, not a promise of immortal registration. [FLP reference](https://developers.google.com/android/reference/com/google/android/gms/location/FusedLocationProviderClient)

Framework exposes provider-specific PendingIntent updates throughout the supported API range. Passive delivery can remain sparse and subject to background limits; no route or fast motion wake follows from registration. [LocationManager](https://developer.android.com/reference/android/location/LocationManager), [background Location limits](https://developer.android.com/about/versions/oreo/background-location-limits)

### 2.2 Receiver admission and durable authority

Choose a bounded receiver→existing ingress path, not an alternate writer:

1. Decode only the exact expected result/action and opaque registration identity; reject unknown/cancelled generations. `goAsync` performs off-main work and always calls `finish`.
2. Proposed receiver admission budget5s; cap a delivered payload at64 locations. Copy/sort a bounded set by provider elapsed time, qualify each, persist the accepted prefix through existing source ingress, and record a typed overflow/admission gap when storage permits. A received batch larger than the bound cannot silently become “complete”. No unbounded array-to-list materialization or DB migration inside receiver work.
3. Resolve registration residency, boot, physical fingerprint, observed-time authorization, ambient consent/envelope, collected/deletion epoch and source retention in Room before acceptance. No session object is consulted for baseline eligibility. Provider acceptance time fences pre-registration cached points.
4. Request existing durable materialization/recovery work after WAL acceptance. WorkManager can drain/reconcile later; it is not a high-frequency acquisition host and cannot make a lost callback durable retroactively. If storage/startup is unavailable beyond the budget, report lost/unknown coverage when next possible; never claim retry will recover an unpersisted OS payload.
5. New same-boot process can authenticate a SYSTEM_REARMABLE generation with null process-incarnation ownership; old PROCESS_BOUND generations remain invalid after process death. Registration metadata ACTIVE does not by itself prove Android currently holds the request. On uncertain state, remove/reconcile exact old identity before registering a successor.

The5s/64-location bounds are explicit new implementation constants proposed for this narrow receiver. Existing64 callback-lane capacity has different units. Android receiver work is time-bounded and delivery is not guaranteed; this design does not assert completion under arbitrary device/storage stalls. [Broadcast lifecycle](https://developer.android.com/develop/background-work/background-tasks/broadcasts), [PendingIntent security/identity](https://developer.android.com/reference/android/app/PendingIntent)

**Storage contract agreed with Data:** one protected canonical sample per original accepted physical delivery/content receipt; a sample-linked common receipt holds event/registration/sequence/writer/hash/time uncertainty/boot/clock/data epoch. Separate purpose-association rows authenticate captured logical/run/segment/manifest or ambient intent/policy/consent/envelope/effective interval. Ambient has no session columns populated. Cursor plus association commit after exact canonical receipt validation; sample-before-association crash is reconciled idempotently. Deleting one purpose association does not erase a surviving lawful purpose; last-purpose/full-source deletion purges sample/receipt under fences. Source sequence0 remains valid. Full schema/retention details are in DATA_GAP_CLOSURE.

### 2.3 Active Location and transport transitions

Keep current callback/listener transport for active acquisition. When capture, active baseline, game or explicit current-position demand requires it, the shared owner uses the strongest compatible **authorized** request and publishes separate purpose eligibility. One accepted callback can serve independently authorized capture and baseline without duplicating the sample. A feature-only fix has no capture/ambient persistence eligibility merely because the physical owner exists.

Choose **remove-ack-before-add** when switching passive PendingIntent ↔ active callback, backend, or an incompatible physical plan. Persist cutoff/retirement debt; stop admitting against the retired identity; remove exact old handle; then reserve/register/acknowledge successor. If removal fails, do not install another competing handle. Keep unchanged compatible callback registrations for authority-only changes. Admit old queued points only when their observed interval and already-accepted prefix remain inside the old authority; never borrow successor authority. Surface the possible handoff gap. This favors correctness and reuse over an unproved zero-gap claim.

Alternative considered: use one PendingIntent transport for every mode, replacing its request in place. It simplifies transport count, but changes the established foreground callback path and makes old/new queued-delivery attribution harder. Reject as the default for this slice. Alternative make-before-break needs explicit dual-generation overlap/dedup proof and more code; do not introduce it merely to promise seamlessness.

Provider mapping is explicit: FUSED uses existing priority mapping. FRAMEWORK uses network for low-power/balanced when supported, GPS for high accuracy when permitted, and records actual provider/fallback. Missing GPS/network does not become successful active quality because PASSIVE was accepted. Approximate permission can yield approximate evidence; missing accuracy is unknown, never0m. No GMS dependency installation, GPS hardware requirement, network client or separate geocoding provider is added.

### 3.2 Recovery and loss of capability

- Reuse startup/deletion gate, exact descriptor/command reconciliation, owner retirement and existing boot/package-replaced scheduling. Boot work re-arms eligible passive/system registrations and reconciles stored intent; it does not reconstruct a foreground exemption or resurrect ended live focus.
- Same-boot active manual recovery may continue only under existing exact descriptor and actual permitted Android redelivery/entry. A new service run has a new identity. Reboot invalidates monotonic leases/hints; automatic focus needs fresh control, and manual interrupted organization ends at its last trustworthy boundary unless a new explicit resume policy is approved. Preserve historical evidence/gaps.
- Force-stop/task-manager stop and package reset cannot be advertised as automatic recovery. On the next allowed launch reconcile old generations and stopped state, show interruption and request explicit action where needed. Do not schedule exact alarms or abuse background exemptions to defeat user stop.
- Permission/source off commits an admission fence before retirement. A new permission grant re-evaluates saved intent; it grants neither capture enrollment nor background expansion. Available siblings continue. A source-local failure cannot globally stop otherwise valid acquisition; shared corruption/startup deletion authority failure can legitimately block all writes.
- On temporary total provider loss, retain visible interrupted live intent only while the existing legal host/recovery contract permits it; no unbounded providerless shell. MAIN's30s cold-start shell remains the bound, not a permanent keepalive. An unmet soft quality upgrade preserves useful baseline and does not end the organization.
- Preserve audit-reconciliation's durable-stop-before-foreground-release invariant while adapting it to remaining baseline/feature demands. Its power-save observer must feed the new single arbiter rather than remain another behavioral writer.

If an existing hard contract becomes impossible, mark that consumer suspended and retain other independently valid demands. One source's no-plan is not a global fatal result.

### 5.2 Deterministic candidate choice under power pressure

Use a finite list generated by the existing factory: requested profile, current compatible plan, supported batch variants, cheaper acquisition modes within the source's explicit envelope, and disabled only when no authorized useful demand exists. No cross-source optimizer and no new helper sensor. Clamp preferred timing to real user limits without relaxing evidence acceptance thresholds. Discard candidates violating genuine source floors, wake/recovery, host legality or capabilities.

The existing qualitative estimator compares three sustained drivers: acquisition, wake/delivery, and processing/durable IO. Each uses `LOW/MEDIUM/HIGH/UNKNOWN` qualitative priors, plus actual acknowledged owner/shared-host and remaining optional budget. Switching is a separate transition gate below. These are comparison categories, not additive measured watts or a general weighted score. Count shared hardware once; additional purpose materialization can still add IO. No “free Steps”, unconditional idle-host charge or recurring scan charge after the finite budget is consumed.

**Executable savings comparator:** for current compatible plan `p` and feasible candidate `c`, a saving is established only when all three driver comparisons are known, `cost(c,d) <= cost(p,d)` for every driver `d`, and at least one is strictly lower, using `LOW < MEDIUM < HIGH`. Any relevant UNKNOWN, all-equal result, or crossed tradeoff (one driver improves while another worsens) rejects that candidate as an optional saving. If none qualifies, retain `p`. No weighted sum breaks a crossed tradeoff. This rule governs optional savings only: user changes, restored quality preference, new hard obligations, revocation and safety/legality follow their own higher-priority rules even when their necessary plan costs more. If current is no longer compatible, use ordinary feasible-plan resolution rather than retaining it under this comparator.

For multiple candidates that each pass against current, select the first in this fixed source-specific order. Prefer unchanged physical fingerprint first within that qualifying set; then use the table, then ascending canonical physical fingerprint as the final deterministic tie. Candidates may differ from one another, but every selected candidate must independently improve current without a worse sustained driver. Only the finite factory-produced values are considered; this does not invent intermediate modes, backends or timings.
