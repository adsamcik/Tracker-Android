Baseline: `037eb7e9b2c4f902aec46d5a85f3c43a59172b72`. Static source inspection only; all authored tests are NOT_RUN.

1. `StepsGoalDecisionReconciler.record` and `StepsGoalHistoricalReconciler.revisedCandidate` create pristine revision-one candidates. `StepsGoalEffectDao.recordDecision` assigns a higher revision whenever desired points/XP, result, policy, calendar or source-result digest changes. Its `hasSameDecision` deliberately excludes diagnostic time and the global evidence counter. A semantically unchanged refresh can advance `updatedAtMs` without rearming actions. That is the only legitimate changing-time/same-effect-revision case found, and the selected projectors retain an existing zero receipt's time for it.
2. `StepsGoalRewardProjector.projectPoints` is the only production caller of `PointsAwardedDao.applyGoalEffect`. `PlayerProgressionRepository.applyStepsGoalXpInsideAcceptedGeneration`, invoked by that projector, is the only production caller of `XpLedgerDao.applyStepsGoalEffect`. Both read current desired effect identity/revision. Points acknowledgement checks the exact current effect again; XP ledger/profile/ack share AppDatabase's transaction. Exceptions preserve pending authority through the existing component retry result. The raw SQL update methods have no other production callers.
3. `StepsGoalCoordinator` composes current period decisions, historical repair, reversible rewards and one-time notification claims. It has no production caller and is documented as deliberately dormant. This packet does not activate it or alter that boundary. Authored Room projector cases prove source assertions only, not a live chain.
4. Native session fact projection, daily repair, portable Steps import, selected session deletion and retained Steps pruning already queue historical goal repair. Native all-day `deleteAmbientStepsAfterConsentReset` previously advanced evidence after authenticated removal without this queue connection. The selected source adds the existing conservative `enqueueAllStepsGoalRepairs` in its existing transaction. Existing effect rows stay intact for qualified recomposition from surviving sibling evidence; the queue marks only goal streak/perfect-week achievement authority materializing as it does elsewhere.
5. `PointsDomainEventConsumer` schedules `PointsWorker` only on physical `DomainEvent.SessionEnded`. The worker reads a physical Trip projection, scores cached distance/duration and deduplicates by end timestamp/source. `GameDomainEventConsumer` calls `PlayerProgressionRepository.awardSessionXp`, which likewise scores cached physical segment distance/duration and inserts an immutable SESSION/sourceId row. Neither is a correction-safe logical source effect.
6. `DefaultTripRepository.deleteTrip` deletes `session_segment` directly. It does not retract either legacy SESSION reward. Points legacy rows have no source identity beyond timestamp/source; two recordings can end at the same millisecond, and a corrected time can no longer identify the old row. Existing GOAL receipt repairs cannot safely be presented as SESSION repairs.

No invented Activity, Pressure, Wi-Fi or Cell reward is added. Native observations, imported data and retrospective annotation are not interchangeable reward authority. The unresolved prospective SESSION contract is kept explicit in `SESSION_REWARD_GAP.md` rather than selecting a frozen awards draft.

V1 review also identified a higher-revision legacy XP ownership hole. V2 guards `sourceId != null` before both replay/replacement branches and independently requires SQL `source_id IS NULL`; neither the current goal projector nor a direct higher-revision DAO update can repurpose that receipt. A refused current desired effect becomes the existing retryable component failure, with no XP acknowledgement, profile mutation or metric dirty handoff. Valid independent Points retraction can still settle without pretending the XP component succeeded.
